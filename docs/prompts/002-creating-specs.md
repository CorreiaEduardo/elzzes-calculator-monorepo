## Creating the specs

> This is a transcribed version of a brainstorming session that I dictated to an AI, asking it to summarize and better structure the content into a prompt.

Okay, I want to turn the calculator brief in problem.md into a proper set of specs before anyone writes a line of code. problem.md is the lighthouse: if anything I say here disagrees with it, problem.md wins. I want this as a documentation baseline, no implementation yet, I'd rather argue about the contract now than refactor later. The front end never computes — not with JS operators, not with eval, not as a "responsiveness optimization." Arithmetic has exactly one implementation, in Go, and that invariant holds over everything else. We're building it as a monorepo, and the stack is agreed and closed as we defined in architecture files. Don't add a dependency, abstraction, or process beyond that stack unless there's a requirement and I've agreed to it.

Numbers are IEEE-754 binary64 end to end. No rounding in the API. Negative zero normalizes to
zero. Check the divisor before dividing, including -0. Any NaN or infinity becomes a
NON_FINITE_RESULT error. 0^0 = 1; zero to a negative exponent is non-finite; a negative base
with a fractional exponent is undefined; underflow to zero is accepted. Percentage is unary: x /
100. The UI formats for display — 12 significant digits, exponential thresholds, no grouping
separators, a 15-digit input cap, and WYSIWYG chaining where the displayed formatted value is
what carries into the next operation. The raw API value stays unrounded.

The UI is a familiar 4-column keypad with an advanced strip above it. Immediate execution, two
operands, no expression parser or precedence. √ and % apply immediately to the displayed value;
xʸ is binary. One request in flight at a time, AC aborts, late responses are discarded. Domain
errors clear the pending operation and keep the last value; transient errors keep the expression
and = retries. Eleven, no, ten seconds is the client timeout. Errors are inline, in an alert
region, never modals or toasts, and never move focus. Keyboard operation is complete, with
visible focus, accessible names, 44px targets, polite live-region updates on the expression
line, aria-busy while calculating, reduced-motion support, and a responsive mobile-first layout.
Light and dark follow the OS. The UI library is controlled and presentational: Tailwind tokens,
CVA/clsx, no fetch, no arithmetic, no operation vocabulary, and Storybook stories for variants
and states.

What I want out of this pass is the specs themselves — docs/specs, four of them, numbered 001 through 004, each its own folder with a SPEC.md, plus an INDEX.md that shows what each spec covers, what it depends on, its status, and how it traces back to the brief. Treat this as me defining the steps to the finished product and asking you to write them down: 001 the mandatory operations and the contract, 002 the optional operations and their domains, 003 the UI, 004 delivery and verification. The order of work is 001 → 002 → 003 → 004, because the contract is fixed before the UI is built and delivery can only be verified once there's an app and tests; implementation may overlap once the contract is agreed, but every change stays independently reviewable. Status vocabulary is proposed, scoped, in progress, implemented, superseded — this baseline should come out scoped. Every spec follows the same shape: what is it, scope in and out, semantics and edge cases, acceptance criteria, tests, decision, reasons, rejected alternatives, open questions. And no duplicated definitions: each topic has exactly one canonical document. The wire contract lives in openapi.yaml, operation behavior and edge cases in specs 001 and 002, UI behavior in DESIGN.md, structure and numeric model and deployment in ARCHITECTURE.md, invariants in PRINCIPLES.md, implementation detail in each component's CONVENTIONS.md, and verification and coverage in 004. Specs link to those instead of restating them; if two documents disagree, stop and reconcile before coding.

001 is the four mandatory operations — add, subtract, multiply, divide — delivered end to end: Go domain functions, the HTTP API, the typed client, the keypad, and tests. The big contract call is one endpoint, POST /api/v1/calculate, discriminated by an operation field, with fixed arity per operation, one shared error envelope, and a versioned /api/v1 path so a breaking change has somewhere to live. I considered one endpoint per operation and rejected it — more routes, duplicated decode and validation, no benefit for a fixed vocabulary — and I want the spec to also record why we rejected n-ary operands, client-side arithmetic, exact rational or decimal arithmetic, and an operation-discovery endpoint. Validation is shared by every operation and strict: content type, body present and under the contract's size limit, top-level JSON object, no unknown fields, operation required and known, exact operand count, operands that are real JSON numbers — no strings, no nulls, no 1e999 — and a finite result. Operands are IEEE-754 binary64 decoded from JSON; results are unrounded, operands are echoed back, negative zero is normalized to zero. Division by zero, including a negative-zero divisor, is 422 with an fixed error code. Overflow to infinity is 422 with the respective fixed error code, for all four operations; underflow to zero is accepted, not an error. Malformed payloads get the documented 400, 413, or 415 — missing body, invalid JSON, wrong top-level type, unknown field, missing or unknown operation, zero, one, or three operands, string or null operands, out-of-range numbers, wrong content type, oversized body. GET on the calculate route is 405 method not allowed, and an unknown /api path is 404 not found. Large and tiny operands within range round-trip through JSON without rejection, signs and decimals are preserved, and 1 ÷ 3 is the binary64 approximation — tests use tolerance or assert the formatted display, never string equality of the raw float. Every case in that matrix gets at least one Go test, table-driven in the domain and httptest at the HTTP layer; the service never panics; the web client's MSW fixtures derive from the OpenAPI examples; and the UI-side handling of division by zero and generic errors belongs to 003. The UI must never compute — the request is the calculation, and the tests have to show that.

002 is the three optional operations — power, sqrt, percent — through the same endpoint and the same keypad, and the decision is to include them rather than skip them: they cost one domain function, one registry entry, and three keys each, and they prove the contract handles unary as well as binary arity. Power is binary and uses math.Pow; sqrt is unary, the principal square root via math.Sqrt, domain operand greater than or equal to zero; percent is unary and defined as x / 100. Any non-finite result is the same 422, specially a negative base with a fractional exponent. sqrt of a negative operand is its own 422 error code, huge-but-finite values stay finite or produce NON_FINITE_RESULT if they genuinely overflow. Wrong arity is 400 with a fixed error code and an unknown operation is also 400 with its fixed error code.  On the keypad, xʸ, √, and % apply to an entry or to a result, and unary keys are no-ops when the second operand is empty. The test story mirrors 001. Rejected and worth recording: contextual percentage like 200 + 10% = 220 — ambiguous and needs pending-operation introspection we deliberately don't have, which is why percent is unary.

003 is the whole UI for all seven operations, and DESIGN.md is canonical for behavior; the spec scopes it and defines acceptance. React and TypeScript, one useReducer state machine with immediate execution. No expression parser, no precedence, no repeated-equals, no memory keys, no history or persistence or localStorage, no accounts, no i18n, and no user-selectable themes. The reducer owns entry rules, operator replacement, chaining, equals, unary application, the in-flight lock, AC abort, and error recovery. One request in flight: the reducer locks math keys while calculating, AC aborts and resets, and a late response can never mutate state. Requests go through a TanStack Query mutation with automatic retry disabled and an AbortController signal, to a relative /api/v1/calculate, JSON only, with no CORS and no absolute host in code. Zod validates every response at the boundary, timeouts, transport failures and malformed response maps to its respective error codes. 4xx and 5xx get the friednly copy and recovery rules in DESIGN.md. Loading, success, domain-error, and transient-error states all exist, and every error path allows recovery or retry without a reload. The web app may parse what the user typed and format what the server returned; it may not compute, negate a computed result, or use eval. Presentation splits into @elzzes/ui as controlled components, tokens, and stories only — no fetch, no arithmetic, no operation vocabulary, no global state; the web app composes them. Responsive down to 360px with the documented target sizes and no horizontal scroll. Every entry rule, formatting rule, and reducer transition gets a test; component tests cover names, keypad interaction, keyboard shortcuts, busy state, alert, and focus. Tests assert the client call rather than trusting displayed output, and no arithmetic implementation, API call, or fetch may exist in @elzzes/ui. 

004 is delivery and verification — what makes the app reproducible and reviewable. Two multi-stage Dockerfiles, one per service, orchestrated by compose.yaml, so docker compose up --build from a clean clone serves the SPA at localhost:8080 with the API on the same origin. The web image installs with pnpm, builds the SPA, and copies the static output plus the Nginx config into an unprivileged Nginx listening on 8080; Nginx does history fallback and proxies /api/ and /healthz to api:8080, which is why no CORS is required. Final images contain no dev server, no Node or Go toolchain, no source, and no secrets; the stack needs no volumes, database, or external network beyond the published port. The brief asked for a "Dockerfile to run frontend + backend together" I'll read that as two service Dockerfiles plus Compose. GitHub Actions runs on push and pull requests, mirrors the local procedure exactly, uses pnpm install --frozen-lockfile and the Go module cache, builds Storybook and the production frontend, and fails on any lint, typecheck, test, coverage, or build failure; it doesn't deploy, publish images, or require secrets, also no secrets in the repo. Done means tests, typecheck, vet, lint, coverage, and CI green, docs current, and the change revertable as one unit.

So expand this naturally into the four specs under docs/specs, with the INDEX, in the format and order above — each spec complete enough to hand to an implementer, each pointing at the canonical documents rather than copying them, each carrying its decisions, reasons, rejected alternatives, open questions, and the edge-case matrix that will later become test names. If something here is ambiguous or conflicts with problem.md, flag it and ask before inventing a decision.
